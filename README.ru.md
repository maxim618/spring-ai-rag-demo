Исследовательский проект для изучения особенностей **Spring AI 2.0** с интеграцией  LLM и построением RAG-системы (Retrieval-Augmented Generation).

Проект демонстрирует последовательную реализацию компонентов RAG-системы: загрузку базы знаний, векторный поиск, семантическую идентификацию вопросов и обработку изображений с помощью Vision-модели.

## Практический сценарий

В качестве сценария используется чек-лист курьера службы доставки.

Во время открытия смены курьер может повторить стандарты доставки, а приложение помогает сопоставить заданный вопрос с соответствующим вопросом из базы знаний.

Проект демонстрирует, как объединить структурированные данные, векторный поиск, языковые модели и обработку изображений в одном Spring Boot приложении.

## Реализованные возможности

- Интеграция Spring AI с OpenAI-совместимым API через OpenRouter.
- Настройка моделей для обработки текста, изображений и создания embeddings.
- Загрузка Checklist Knowledge Base из JSON-файла.
- Преобразование вопросов и вариантов ответов в документы Spring AI.
- Интеграция PostgreSQL и PGVector.
- Загрузка документов в векторное хранилище при запуске приложения.
- Поиск семантически похожих вопросов с использованием vector retrieval.
- Идентификация вопросов с помощью LLM на основании найденных кандидатов.
- Проверка результата идентификации относительно списка найденных кандидатов.
- Обработка неоднозначных и неидентифицированных вопросов.
- Извлечение текста вопроса и вариантов ответов из скриншота с помощью Vision-модели.
- Поддержка текстового и графического способов ввода.
- Обработка ошибок внешних AI-провайдеров и безопасная передача ошибок через HTTP API.
- Автоматизированные тесты компонентов и сценариев распознавания скриншотов.
- Локальная конфигурация приложения с использованием micro-env.

## Как работает идентификация вопроса

### 1. Подготовка базы знаний

Checklist Knowledge Base загружается из JSON-файла.

Каждый вопрос содержит:
- уникальный `Question ID`;
- текст вопроса;
- тип вопроса;
- варианты ответов;
- правильные варианты ответов.

Для векторного поиска каждый логический вопрос преобразуется в один документ Spring AI.

Текст документа включает каноническую формулировку вопроса и варианты ответов. Идентификатор вопроса и его тип сохраняются в metadata.

Для обеспечения стабильности при повторной загрузке используется детерминированный технический `Document.id`, сформированный на основе `Question ID`.

### 2. Векторный поиск

При запуске приложения документы Checklist Knowledge Base загружаются в PGVector.

При поступлении вопроса приложение выполняет векторный поиск и получает наиболее похожие документы.

Результаты поиска используются как кандидаты для последующего этапа идентификации. Сам по себе результат vector retrieval не считается подтверждённой идентификацией.

### 3. Идентификация вопроса

LLM получает нормализованное представление вопроса и список найденных кандидатов.

Приложение проверяет результат и не допускает выбора идентификатора, отсутствующего среди переданных кандидатов.

Предусмотрены три результата:
- `Identified` — вопрос надёжно идентифицирован;
- `Ambiguous` — найдено неоднозначное соответствие;
- `NotIdentified` — надёжное соответствие не найдено.

После успешной идентификации приложение получает каноническую запись вопроса из Checklist Knowledge Base по `Question ID`.

В случае неоднозначной или неуспешной идентификации приложение не выбирает ближайший результат автоматически.

### 4. Распознавание скриншотов

В качестве альтернативы текстовому вводу приложение принимает изображение чек-листа.

Vision-модель извлекает текст первого (верхнего) вопроса и доступные варианты ответов.

Распознанная информация преобразуется в то же нормализованное представление, которое используется при текстовом вводе.

Далее применяется общий pipeline идентификации:
- векторный поиск кандидатов;
- семантическая идентификация;
- проверка результата;
- получение канонической записи из базы знаний.

Если верхний вопрос невозможно надёжно прочитать, приложение возвращает соответствующую ошибку вместо попытки идентифицировать другой вопрос на изображении.

В текущей реализации обрабатывается один скриншот за запрос и идентифицируется первый (верхний) вопрос.

## Архитектура

Основной pipeline идентификации:

```text
             Текстовый ввод
                    |
                    |
Скриншот            |
    |               |
    v               |
Vision-модель        |
    |               |
    +-------+-------+
            |
            v
Нормализованное представление вопроса
            |
            v
ChecklistKnowledgeBaseRetriever
            |
            v
       PGVector
            |
            v
Список кандидатов
            |
            v
LlmQuestionSemanticMatcher
            |
            v
ChecklistQuestionIdentifier
            |
            v
Проверка результата идентификации
            |
            v
        Question ID
            |
            v
Получение канонической записи
из Checklist Knowledge Base
            |
            v
     HTTP Response
```

Основные компоненты приложения:

- `ChecklistKnowledgeBaseLoader` — загрузка базы знаний.
- `ChecklistKnowledgeBaseVectorStoreLoader` — подготовка и загрузка документов в PGVector.
- `ChecklistKnowledgeBaseRetriever` — поиск кандидатов.
- `ScreenshotQuestionExtractor` — извлечение вопроса из изображения.
- `OpenRouterScreenshotVisionClient` — взаимодействие с Vision-моделью.
- `LlmQuestionSemanticMatcher` — семантическое сопоставление вопросов.
- `ChecklistQuestionIdentifier` — проверка результата идентификации.
- `ChecklistService` — координация процесса.
- `ChecklistQuestionController` — REST API.

## REST API

Приложение предоставляет два основных способа идентификации вопросов.

### Текстовый ввод

`POST /checklist/questions/identify`

Пример запроса:

```json
{
  "text": "Передача заказа гостю. Выберите все верные утверждения:",
  "answerOptions": [
    "При встрече с гостем необходимо поприветствовать его",
    "Обратиться к гостю по имени",
    "Пожелать приятного аппетита"
  ],
  "selectedOptions": ["A", "B"]
}
```

### Ввод изображения

`POST /checklist/questions/identify-screenshot`

Тип запроса: `multipart/form-data`.

Имя параметра изображения: `image`.

Поддерживаемые форматы: JPEG, PNG и WebP.

### Результаты обработки

| HTTP Status                | Назначение                                                        |
|----------------------------|-------------------------------------------------------------------|
| `200 OK`                   | Вопрос успешно идентифицирован                                    |
| `400 Bad Request`          | Некорректный запрос или изображение                               |
| `409 Conflict`             | Неоднозначная идентификация                                       |
| `422 Unprocessable Entity` | Вопрос не удалось надёжно идентифицировать или распознать         |
| `502 Bad Gateway`          | Некорректный ответ сервиса идентификации                          |
| `503 Service Unavailable`  | Временно недоступен поиск из-за ограничения провайдера embeddings |

При успешной идентификации API возвращает канонический вопрос, его тип, варианты ответов и доступную оценку уверенности.

Текущая реализация идентифицирует вопросы и возвращает их каноническое представление. Проверка выбранных ответов и выдача правильных вариантов ответов пока не входят в реализованный функционал.

## Конфигурация

Основные настройки приложения находятся в:

`src/main/resources/application.properties`

Локальная конфигурация загружается с помощью библиотеки [micro-env](https://central.sonatype.com/artifact/io.github.maxim618/micro-env)

Файл `micro-env.list` определяет расположение локальных файлов конфигурации:

```text
secrets/openrouter=.env
secrets/db=.env
```

В репозитории находятся примеры конфигурационных файлов:

```text
secrets-example/
├── openrouter/
│   └── .env
└── db/
    └── .env
```

Используются следующие параметры:

| Переменная           | Назначение                          |
|----------------------|-------------------------------------|
| `OPENROUTER_API_KEY` | Ключ доступа к OpenRouter           |
| `DB_URL`             | JDBC URL PostgreSQL                 |
| `DB_USERNAME`        | Пользователь PostgreSQL             |
| `DB_PASSWORD`        | Пароль PostgreSQL                   |
| `KNOWLEDGE_FILE`     | Путь к JSON-файлу базы знаний       |
| `SCREENSHOT_MODEL`   | Модель для распознавания скриншотов |

Для некоторых параметров предусмотрены значения по умолчанию в `application.properties`.
