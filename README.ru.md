# Spring AI RAG Demo

Учебный проект для изучения **Spring AI 2.0**, с интеграцией  LLM и построением RAG-системы (Retrieval-Augmented Generation).

Проект развивается примерно так: от интеграции с языковой моделью к загрузке базы знаний, векторному поиску и идентификации вопросов по содержимому чек-листа.

## Практический сценарий

В качестве учебного сценария используется чек-лист курьера службы доставки.

Перед началом смены курьер может повторить стандарты доставки, а приложение помогает сопоставить заданный вопрос с соответствующим вопросом из базы знаний.

Проект позволяет изучать, как объединять структурированные данные, векторный поиск и языковую модель в одном приложении.

## Что реализовано

- Приложение на Spring Boot с использованием Java 21.
- Интеграция со Spring AI и OpenAI-совместимым API через OpenRouter.
- Настройка модели чата и модели эмбеддингов.
- Загрузка базы знаний из JSON-файла.
- Преобразование вопросов и вариантов ответов в документы для векторного хранилища.
- Интеграция с PostgreSQL и PGVector.
- Загрузка документов в векторное хранилище при запуске приложения.
- Поиск наиболее похожих документов по тексту вопроса.
- Идентификация вопроса чек-листа с помощью языковой модели и проверка результата относительно найденных кандидатов.
- Обработка некорректных ответов LLM и тестирование соответствующего поведения.
- Логирование технических ошибок при вызове модели и преобразовании её ответа.

## Как устроен процесс

### Подготовка базы знаний

База знаний загружается из JSON-файла. Каждый вопрос содержит идентификатор, текст, тип и варианты ответов.

При подготовке документов для PGVector текст вопроса объединяется с его вариантами ответов. Идентификатор вопроса и тип сохраняются в метаданных документа.

### Векторный поиск

При запуске приложения база знаний преобразуется в документы и загружается в PGVector.

Для входящего вопроса выполняется поиск трёх наиболее похожих документов. Найденные документы используются как кандидаты для следующего этапа.

### Идентификация вопроса

Языковая модель получает исходный вопрос и список найденных кандидатов. Результат проверяется приложением: модель не должна возвращать идентификаторы вопросов, которых нет среди переданных кандидатов.

Приложение различает успешную идентификацию, неоднозначный результат и ситуацию, когда надёжное совпадение не найдено.

Если модель возвращает некорректный ответ или возникает ошибка обработки, приложение преобразует техническую ошибку в контролируемое исключение. В HTTP-ответе не раскрываются внутренние подробности ошибки.

## Архитектура

```text
JSON-база знаний
       │
       ▼
ChecklistKnowledgeBaseLoader
       │
       ▼
ChecklistKnowledgeBaseVectorStoreLoader
       │
       ▼
     PGVector

Вопрос пользователя
       │
       ▼
ChecklistKnowledgeBaseRetriever
       │
       ▼
Три наиболее похожих документа
       │
       ▼
LlmQuestionSemanticMatcher
       │
       ▼
ChecklistQuestionIdentifier
       │
       ▼
Проверка результата
       │
       ▼
ChecklistService
       │
       ▼
ChecklistQuestionController
       │
       ▼
HTTP-ответ
```

На этой схеме представлен текущий процесс определения вопросов. Приложение извлекает соответствующие вопросы из   
чек-листа и с помощью большой языковой модели (LLM) находит среди них наиболее подходящий.  
Генерация ответов с пояснениями на основе полученного контекста - одно из возможных направлений дальнейшего развития.

## Конфигурация

Основные настройки находятся в `src/main/resources/application.properties`.

Приложение использует следующие переменные окружения:

| Переменная           | Назначение                    |
|----------------------|-------------------------------|
| `OPENROUTER_API_KEY` | Ключ доступа к OpenRouter     |
| `KNOWLEDGE_FILE`     | Путь к JSON-файлу базы знаний |
| `DB_URL`             | JDBC URL PostgreSQL           |
| `DB_USERNAME`        | Пользователь PostgreSQL       |
| `DB_PASSWORD`        | Пароль PostgreSQL             |

Для `KNOWLEDGE_FILE` и параметров базы данных предусмотрены значения по умолчанию в конфигурации приложения.

  В проекте используется библиотека `micro-env` для подключения конфигурации из локальных файлов; 
`micro-env.list` указывает на файл `.env` с настройками для OpenRouter.

## Запуск PostgreSQL и PGVector

В корне проекта находится `docker-compose.yml`, который поднимает PostgreSQL с расширением PGVector.

```bash
docker compose up -d
```

По умолчанию контейнер использует:

- База данных: `rag`
- Пользователь: `rag`
- Порт: `5432`

Для локального учебного запуска эти значения согласованы с `application.properties`. 
Не используйте такие простые учётные данные в публично доступном или production-окружении.

## Запуск приложения

Должны быть установлены Java 21, Maven и Docker.

1. Запустите PostgreSQL с PGVector:

   ```bash
   docker compose up -d
   ```

2. Настройте ключ OpenRouter через поддерживаемую локальную конфигурацию.

3. При необходимости укажите собственный файл базы знаний через `KNOWLEDGE_FILE`. По умолчанию используется `data/checklist-knowledge-base.example.json`.

4. Запустите приложение:

   ```bash
   mvn spring-boot:run
   ```

## Тестирование

Запустить тесты:

```bash
mvn clean test
```

Проверить сборку и интеграционные тесты, если они настроены в проекте:

```bash
mvn clean verify
```

Тесты компонентов позволяют проверять обработку ошибок и взаимодействие с зависимостями без обязательного обращения к реальной языковой модели в каждом тесте.
